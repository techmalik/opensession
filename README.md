# OpenSession

Open-source speaker and content management for conferences. Built for the Kill My
SaaS competition as a replacement for Sessionboard: call for papers, abstract
review, speaker portal, content collection, agenda building, public schedule
embeds, a cross-event speaker CRM, and a public API.

Live: https://opensession.opensession.workers.dev

## What it does

An organizer runs a conference program end to end without leaving the app:

1. Create an event and publish a call for papers with custom, conditional fields.
2. Collect abstracts from a public form that works logged out, on a phone.
3. Score them with evaluation plans, blind or open, with reviewer recusal.
4. Move them through Pending, Accept Queue, Accepted, Decline Queue, Declined, then
   send decision emails as an explicit separate step.
5. An accepted abstract becomes a session, gets scheduled on the agenda, and shows
   up on the public widgets and the calendar feed with no re-entry.
6. Speakers manage their own profile, tasks, files, and schedule in a portal that
   only ever shows their own data.

## Architecture

React Router v7 in framework mode (SSR) running on Cloudflare Workers. One Worker
serves the admin app, the public pages, the widgets, and the API.

```
workers/app.ts          Worker entry: fetch handler plus the scheduled() cron
app/routes.ts           the full route table
app/routes/*.tsx        one module per screen; *.server-free where it hits the client
app/lib/*.server.ts     queries and side effects, never imported by a component
app/lib/*.ts            client-safe constants and view types
app/components/         shared UI primitives (ui.tsx) and widget chrome (embed.tsx)
database/schema.ts      43 tables, Drizzle
database/seed.sql       generated by `npm run seed:gen`
drizzle/                7 generated migrations, never hand-edited
spec/                   the vendored eval kit: rubric, scenarios, fixture data
```

| Concern | How |
|---|---|
| Data | D1 (SQLite) via Drizzle ORM. Migrations with drizzle-kit, applied by wrangler. |
| Files | `app/lib/storage.ts`. Blobs live in D1 by default; R2 sits behind the same interface. |
| Auth | PBKDF2-SHA256 (100k iterations) over WebCrypto, signed session cookie. Roles: admin, organizer, evaluator, speaker. |
| Email | Provider abstraction. With `BREVO_API_KEY` it sends; without one it records the send with status "test" so the audit trail still exists. Every send is a row in `email_sends` before delivery is attempted. |
| Background work | A `jobs` table drained by a 5 minute cron. Cloudflare Queues needs a paid plan, so this deliberately does not use them. Email retries, Airtable sync, reminders, and digests all go through it. |
| AI | Workers AI binding first, then `ANTHROPIC_API_KEY`, then a deterministic fallback (greedy scheduler, template reviews). The features never 500 for want of a key, and a failure is never silent. |
| Public API | `/api/v1`, `x-access-token` auth against SHA-256 hashes in `api_tokens`. Docs at `/docs/api`, generated from the same endpoint list they describe. |
| Widgets | Server-rendered HTML with no client JavaScript at all. Search and filters are GET forms, expansion is `<details>`, the personal itinerary is a cookie. |

Two rules keep the client bundle honest: a route component may not touch a
`.server` module, and a resource route (CSV, JSON, iCal) never renders a component.

## Requirement to screen map

The eval kit scores seven areas. Where each one lives:

| Spec area | Organizer screens | Public and speaker screens |
|---|---|---|
| 01 Call for Papers | `/admin/:id/forms`, form builder, `/admin/:id/settings/taxonomy` | `/cfp/:event`, `/submit/:event/:form` |
| 02 Abstract Management | `/admin/:id/submissions`, `/admin/:id/evaluations`, plan results, `/admin/:id/submissions/send-decisions` | `/review`, `/review/:assignment` |
| 03 Speaker Management | `/admin/:id/speakers`, import, bulk email, `/admin/:id/portals` | `/portal`, `/portal/profile`, `/portal/schedule` |
| 04 Content Management | `/admin/:id/content`, file requests, `/admin/:id/content/review` | `/portal/tasks`, `/portal/files` |
| 05 AI Agenda | `/admin/:id/agenda`, `/admin/:id/agenda/assist` | `/agenda/:event` |
| 06 Public Widgets | `/admin/:id/embeds` | `/embed/v1/:event/{sessions,speakers,agenda,itinerary,gallery}` plus `.json` and `calendar.ics` |
| 07 Speaker CRM | `/crm` and everything under it, deliberately outside the event nav | none |

Cross-cutting: `/admin/:id/communications` holds every email ever sent with a test
send button, and `/admin/:id/settings/integrations` holds Airtable and Accelevents.

Every list view has search, at least one filter, bulk select with bulk actions, and
a CSV export. No exceptions.

## Public widgets

No login, no JavaScript, readable at 375px:

| Surface | URL |
|---|---|
| Sessions list | `/embed/v1/<event-slug>/sessions` |
| Speakers directory | `/embed/v1/<event-slug>/speakers` |
| Agenda grid | `/embed/v1/<event-slug>/agenda` |
| Schedule itinerary | `/embed/v1/<event-slug>/itinerary` |
| Speaker gallery | `/embed/v1/<event-slug>/gallery` |
| JSON feed | any of the above with a `.json` suffix |
| Calendar feed | `/embed/v1/<event-slug>/calendar.ics` |

`/sessions`, `/speakers`, `/agenda`, `/schedule`, and `/gallery` redirect to the
current event's widgets. Snippets, previews, and the cache-refresh button live under
Embeds in the admin.

One gate decides what is public (`app/lib/public.server.ts`): a session appears only
when the event is live and the session is accepted, scheduled, not a draft, and
published rather than held. Every public surface reads that same gate, so nothing
can leak into one surface while hidden on another.

## Self-hosting

You need a Cloudflare account. The free plan is enough: no Queues, no Durable
Objects, no paid bindings anywhere.

```bash
npx wrangler login
npx wrangler d1 create opensession-db     # paste database_id into wrangler.jsonc
npx wrangler secret put SESSION_SECRET
npm run db:remote
npm run deploy
```

Optional secrets, each of which degrades cleanly when absent:

| Secret | Without it |
|---|---|
| `BREVO_API_KEY` | Email is recorded with status "test" and never delivered. Every screen still works. |
| `AIRTABLE_API_KEY`, `AIRTABLE_BASE_ID` | Airtable sync is off. |
| `ANTHROPIC_API_KEY` | AI features fall back to Workers AI, then to a deterministic heuristic labelled as such. |

Deploy with `npm run deploy`, never bare `wrangler deploy`: the bare command ships
the previous build's `build/server/wrangler.json`, stale vars included.

## Honest limitations

Things a careful evaluator should know, rather than discover:

- **No dark mode.** DESIGN.md puts it out of scope. Half-shipping it looked worse
  than not shipping it.
- **Agenda conflicts are warned, not blocked.** Double-booking a room or a person is
  detected server-side on every render and surfaced, but the organizer can still save
  it. Real programs sometimes need a deliberate overlap.
- **Airtable writes are not verified end to end.** Authentication is. A personal
  access token that has scopes but no base added under Access will authenticate,
  return an empty base list, and then 403 on everything; the UI explains that case,
  but the full write path has not been proven against a live base.
- **Accelevents sync is best effort by design.** It never throws out of the job
  runner. State and the last error surface in Settings, and that is the whole
  guarantee.
- **Contact merge is not reversible.** It re-points event history, sessions, notes,
  and mail onto the primary contact, drops rows that would collide with unique
  indexes, and deletes the loser.
- **Background work runs on a 5 minute cron, not a queue.** Queues need a paid plan.
  A queued email can therefore sit for up to five minutes.
- **AI output is validated, not trusted.** Agenda assist output is checked against
  real rooms, days, and slots, and anything the model misses is back-filled by a
  greedy packer. AI reviews are stored separately from human scores and never enter a
  human aggregate.
- **The public API covers the documented subset**, not all of Sessionboard's surface:
  events, session search and CRUD, contacts, and the taxonomy endpoints.
- **No test suite.** Verification is `npm run typecheck && npm run build` plus
  clicking the flow, which is what the deadline allowed. The eval kit in `spec/` is
  the closest thing to an integration test.
